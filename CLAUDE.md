# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Hackathon prototype (NASA Space Apps 2026, "Field Shift") that compares crop rotations for a field against the observed climate record: soil loss, water-deficit exposure and soil-carbon trend, each with uncertainty. When the data cannot separate two options, the answer is "not resolved" plus what to measure first. The product never calls a language model; explanation text comes from deterministic templates.

The specification is `docs/DEVELOPMENT_BLUEPRINT.md` (read it in full before building anything) and `docs/GETTING_STARTED.md`. Who holds which lane is in `README.md`. Folders are created by the first unit that needs them.

## Commands

Python 3.12, managed with uv. One `pyproject.toml` and `uv.lock` at the repository root, edited only by L2a (platform). Run everything from the repository root.

```bash
uv sync                                  # install, including the dev group
uv run pytest                            # all tests
uv run pytest api/test_cors.py::test_preflight_from_allowed_origin   # one test
uv run ruff check api/ && uv run ruff format --check api/            # lint (scope to your lane's folders)
uv run uvicorn api.main:app --reload     # backend on http://localhost:8000
docker compose watch                     # the whole app: backend on :8000 and frontend on :5173/field-shift-rotation-twin/, both reloading on edits
uv run pip-licenses --with-system --format=json | uv run python -m ci.licences   # licence check
FORBIDDEN_NAMES="$(cat <list>)" uv run python -m ci.names_scan                   # names scan
```

Tests live next to the code they check (`params/test_layout.py`, `validation/test_layout.py`, `api/test_*.py`); `params/` and `validation/` use the standard library only. Docs written before uv existed say `python -m pytest <folder>/`, which still works.

`compose.yaml` runs two services. `api`: the backend image; edits under `api/`, `adapters/`, `contracts/`, `engine/` and `params/` are synced and uvicorn reloads; `pyproject.toml` or `uv.lock` rebuild it. `web`: a Node 22 container running the Vite dev server on the mounted `web/` folder, with `node_modules` in a volume (never in `web/` on the host). `WEB_PORT` and `API_PORT` change the host ports; `CORS_ORIGINS` and `VITE_API_URL` follow them. The `api` service has real climate data switched on (the settings file, the period of D29) with its cache in the named volume `climate_cache` mounted at `/data`, and serves the PLACEHOLDER soil-and-slope example; the image creates `/data` owned by the `app` user so the volume is writable. **A session never sends a rotation request to a stack started this way** (it would call the real service): start it with `POWER_SETTINGS_FILE= CLIMATE_START_DATE= CLIMATE_END_DATE= docker compose up`, which switches the climate source off. Add a new backend folder to the `api` watch list when it is created.

## Platform decisions (L2a)

- Stack: FastAPI served by uvicorn; Pydantic models are the schema format; httpx, numpy, shapely, pyproj; pytest and ruff. Frontend: Node 22 LTS, npm (`package-lock.json` committed, `npm ci` in CI), Vitest; the rest of the frontend stack is in blueprint §4.
- CI: `.github/workflows/ci.yml` runs seven jobs: the six checks `tests` (all pytest, plus ruff on `api/`, `adapters/`, `ci/`), `frontend-build` (`npm ci`, `npm test` (Vitest) and `npm run build` in `web/`; fails if `web/package.json` is missing), `contract-validation`, `secret-scan` (gitleaks over the whole history), `names-scan` and `dependency-licences` (Python with `ci/licences.py`, then the frontend with `ci/frontend_licences.py`, which reads `web/package-lock.json`), plus `image-build`, which builds the `Dockerfile`, starts the image with no configuration and waits for `GET /health` to answer `200` (nothing is pushed). `contract-validation` runs `uv run pytest contracts/` (every folder under `contracts/` ships a test that loads its examples into its models).
- `ci/` holds the check scripts and `ci/test_planted_cases.py`, which shows each check failing on a case planted at run time in a temporary folder (the secret-scan cases need docker). Nothing planted is committed. `ci/allowed_licences.txt` is the Python licence allowlist, with licences written exactly as package metadata reports them; `ci/allowed_frontend_licences.txt` is the npm one, SPDX identifiers as the lockfile records them (PROPOSED). A new dependency with another licence fails CI until the platform developer adds it.
- The forbidden-names list lives in the GitHub Actions secret `FORBIDDEN_NAMES` (one name per line), never in the repository. The scan reports file and line, never the name; without the secret it is skipped with a notice.
- API (`api/`, see `api/README.md`): `create_app(cors_origins, *, climate, soil_slope, engines, rotation_validator, settings)` builds the app. `GET /health` → `{"status": "ok"}` stays at the root; every product route lives under `/api`. `POST /api/rotations/run` is synchronous: a valid request always answers `200` with `outcome`, `result`, `modules` and `sources`, and absences are typed with a reason code of `contracts/CONVENTIONS.md` C3.2, never zero. It also carries `scenarios`, one item per phase (`scenario_id`, `first_ag_year`, `outcome`, `calendar`, `result`, `result_missing`, `modules`); the top-level fields are `phase_1`'s. `4xx`/`5xx` use one shape on every route, `{"error": {"code", "message", "details"}}` (`api/errors.py`).
- Interfaces, not implementations: the route imports only `adapters/ports.py` and `api/ports.py`; implementations are passed into `create_app`. `adapters/ports.py` is the seam between `api/` and `adapters/` (`ClimateSource`, `SoilSlopeSource`, `SourceInfo`): change it only with both sides in the same pull request. Add a real implementation by passing it in, never by editing the route.
- Engine runner (`api/engines.py`): `EntryPointEngines` implements `RotationEngines` on the entry points of `contracts/ENTRYPOINTS.md`. `discover_engine_functions()` imports each engine by its exact module and function name (`engine.calendar.build_rotation_calendar`, `engine.erosion.compute_soil_loss`, `engine.water.compute_water_deficit_exposure`, `engine.amg.run_amg`); one that does not exist is "not built". When a lane lands an engine under that name it is picked up with no change in `api/`. Order: calendar first, then erosion and water with its result, also for an infeasible calendar, then EP5 `run_amg(forcing, parameters=...)` on the `CarbonForcing` built by `api/carbon_forcing.py` (PROPOSED: horizon = whole agricultural years of the record by the start month; `mean_temperature` by D118 from the daily mean of D30; soil properties and starting carbon copied only on an exact quantity (D120, D121); every other quantity missing with its reason, never zero; no forcing, no call). The runner assembles `ResultsPerRotation`: the `amg` rows are the three trend rows of the `CarbonBalance` unchanged, then the `rothc` rows missing `NOT_AVAILABLE` (the mapping of `contracts/ENTRYPOINTS.md`; the balance itself is not in the response); with EP5 not built all six carbon rows are missing as before. It computes nothing scientific, and does not catch what an engine raises (the route answers `500`). Phases (D109, option b, PROPOSED, `api/phases.py`): EP2 runs once; then EP1, EP3 and EP5 run once per phase on a calendar moved so its year `p` comes first (`phase_1` … `phase_N`, N = cycle length; phase 1 is the EP2 calendar unchanged); the rule comes from `engine.calendar.repeat.phase_calendar` / `list_phases` when both exist (#221), else the runner's copy; a component crossing the first year of a phase has no rule (D133): that phase is refused (`result: null`, `NOT_COMPUTABLE`, the `OPEN` case named), never guessed. The parameter catalogue (Q3, D46, D56) is loaded once at start-up from `params/records/` by `load_config` and checked with `check_catalogue`: a problem of loading or checking is a `ConfigError` and the server does not start; an empty catalogue does not stop it. It is passed unchanged as `parameters=` to EP1, EP3 and EP5, always (an engine that does not take it is a `500`); EP2 never gets it. A soil-loss or water engine that is not built gives its part in the not-built form of the results contract (`SoilLossNotBuilt`, `WaterDeficitExposureNotBuilt`, `NOT_AVAILABLE`; decision D12 of #77), so the result is still returned; every other absence (calendar engine not built, an input absent, site data of another field, a bare `Missing` from erosion) keeps `result: null` with `result_missing`.
- The request's `rotation` is loaded into `contracts.rotation_definition.RotationDefinition` by `RotationDefinitionValidator`; an invalid one is `422` `ROTATION_INVALID` and no source or engine is called. Error details never repeat a submitted value. Still stand-ins in `api/standins.py`: the climate source and the soil-and-slope source of the default app when not configured. `ExampleSoilSlopeSource` is wired by `SOIL_SLOPE_EXAMPLE_FILE` and serves the example for any field, under the `case_id` and `field_id` of the request (decision D38 of #77); which file holds the demonstration values is a person's decision.
- Import contract models only as `contracts.<folder>` from the repository root (never `inputs`, `results`): the same class under two names is two classes. Serialise contract models with `model_dump(mode="json")`, never `exclude_none=True`.
- Adapters (`adapters/`, see `adapters/README.md`): `PowerClimateSource(settings, cache, client)` implements `ClimateSource` for NASA POWER. `FileCache` keeps the first response per query (key: SHA-256 of the canonical query) and never overwrites it. A source failure is a result (`unavailable`, `SOURCE_UNAVAILABLE`), never an exception, and is never cached. `PowerSettings` has **no defaults**: parameters, units, community, provenance labels, fill value and reason codes are decisions of people that arrive as configuration. Tests use `httpx.MockTransport` and placeholders; a session never calls the real service. `SoilTableSource(table_paths, groups_path)` (`adapters/soil_tables.py`, PROPOSED) implements `SoilSlopeSource` from soil tables by soil group and a soil-groups declaration that a person supplies (D48, D49): properties copied unchanged, slope missing `NOT_AVAILABLE` (no elevation model decided), an undeclared field `NOT_DECLARED`, an unlisted group `NO_COVERAGE`.
- Configuration (`api/config.py`, PROPOSED): the running app is `build_app(load_config(os.environ))`. Variables: `CORS_ORIGINS`, `POWER_SETTINGS_FILE` (adapter settings JSON; template `adapters/examples/PLACEHOLDER_power_settings.json`, placeholders only), `CLIMATE_CACHE_DIR` (required with it), `CLIMATE_START_DATE` and `CLIMATE_END_DATE` (`YYYY-MM-DD`, both or neither), `SOIL_SLOPE_EXAMPLE_FILE`, `SOIL_TABLE_FILES` (comma-separated) and `SOIL_GROUPS_FILE` (both or neither, never with `SOIL_SLOPE_EXAMPLE_FILE`; templates under `adapters/examples/`). None has a default; blank is unset. Not configured is a typed absence (the stand-ins, no period); configured wrongly raises `ConfigError` naming the variable and the server does not start. `create_app` (in `api/app.py`, re-exported by `api/main.py`) stays the way tests inject fakes.
- Real settings: `adapters/settings/nasa_power.json` holds the adapter settings of the deployed service. Every value is copied from a recorded decision of issue #77 (never chosen while editing); `adapters/test_real_settings.py` checks it against `contracts/CLIMATE_QUANTITIES.md` and against the documented request and response in `docs/evidence/`. The deployed service is switched to real climate data by `POWER_SETTINGS_FILE`, `CLIMATE_CACHE_DIR` and the two dates (table in `api/README.md`). A session never calls the real service.
- CORS: allowed origins come from the `CORS_ORIGINS` environment variable (comma-separated). Unset or empty means no cross-origin access. Compose sets `http://localhost:5173` (Vite dev server); the production origin is set in the host's settings at deploy.
- Deploy: a static frontend and one backend container, both public without login. The frontend: `.github/workflows/pages.yml` publishes `web/dist/` to GitHub Pages on every push to `main` (or by hand, `workflow_dispatch`): base path `/field-shift-rotation-twin/`, hash routing, built with `npm ci && npm run build` in `web/`, with `VITE_API_URL` (a workflow-level value, public, not a secret) set to the backend address. The backend: Railway builds the `Dockerfile` and redeploys on every push to `main`; public address `https://api-production-86e398f8.up.railway.app`. A session never triggers a deploy.
- Not yet agreed or built: the shape of `site` (PROPOSED in `api/rotations.py` as `SiteReference`), the years of climate record requested (no default: without it the climate source is not called), the NASA POWER settings (proposed by lane L0 in #75, for the science reviewers), the point of the series in `SiteClimate` (one pull request with lane L0, model and mapper together), and a compose service serving `web/dist/` once `web/` exists.
- Every library or container image gets a row in `ATTRIBUTIONS.md` (version, URL, licence) when added; only L2a adds dependencies.

## Architecture: lanes, contracts, seams

- **Lanes own folders; never edit another lane's folder.** L0 Core: `contracts/`, `params/`, `engine/erosion/`, `validation/`. L1 Engines: `engine/calendar/`, `engine/water/` (`et0/`, `balance/`), `engine/residues/`, `engine/amg/`. L2a Platform, data and service: `adapters/`, `api/`, CI, deploy, the root Python manifest. L2b Platform, decision and carbon: `decision/`, `engine/rothc/`, `demo/`. L3 Interface: `web/`. Both L2 sub-lanes branch as `l2/<unit>` and count their acceptance limits separately.
- **Contracts first.** Every seam between lanes has a schema plus a hand-written example under `contracts/` (rotation definition, calendar, site data, results, decision output, test plan, saved case, `ResidueLedger`, `CarbonForcing`, `ModelState`, `CarbonBalance`; full table in blueprint §5). Build against the accepted example, not against another lane's unfinished code. Site data and `CarbonForcing` come from L2a; decision output, saved case and the RothC side of the carbon contracts from L2b.
- `contracts/CONVENTIONS.md`: units and direction of each indicator, how uncertainty ranges and missing values (with reason) travel, provenance labels `DECLARED` / `OBSERVED` / `DERIVED` / `SIMULATED`, month and agricultural-year numbering, time zone of daily series.
- `contracts/ENTRYPOINTS.md`: the one public function signature per engine; the API route calls engines only through these.
- `params/` and `validation/` hold record formats and checks only, with placeholder examples; no real values yet.
- Engines are pure functions. Network calls only in `adapters/` (NASA POWER, GPM IMERG, soil and terrain), with the first response cached per case. Thresholds live only in the test plan contract. `demo/` saved cases must open without a backend.

## Rules a session must follow

- **One unit, one branch, one worktree:** `git worktree add ../wt-<unit> -b <lane>/<unit>`, branch names `l0/…`, `l1/…`, `l2/…`, `l3/…`. Never push to `main`, never deploy. Squash-merged PRs only.
- **Never produce** parameter values, thresholds, ranges, expected test values, citations, data-source or dependency choices, or the wording of claims. If one is needed, write `OPEN` or `CITATION NEEDED` and stop; a person supplies it. Never edit expected values in an acceptance test.
- Sessions may propose conventions, contract field lists and test-case designs, marked `PROPOSED`; they take effect only when a person approves the PR (blueprint §3.7).
- Do not add dependencies unless you are working for L2a and the platform developer asked. Do not read or copy code from other repositories.
- A missing value stays missing with its reason; never default to zero or blank. Every displayed number carries its source or an explicit "assumption" mark. Example data is synthetic and labelled as example data on every screen; never use a real producer's field.
- In `web/`, all user-visible text lives in the single English strings file.
- English only everywhere. No secrets, private data, or company/product/personal names in code or data (CI scans for them). No generated images, video or voice.
- A unit is done only with its acceptance test. Validation codes like `[E3]`, `[H2]`, `[D1]` refer to `docs/VALIDATION.md` (written by science reviewers).
- Record every new dataset, library, table or publication in `ATTRIBUTIONS.md` when first used, and add one line per merged unit to `AI_USE_LOG.md`. AI-assisted commits carry a co-author trailer. Commit email must be a non-company address (e.g. GitHub no-reply).
