# Field Shift Rotation Twin

Open-source prototype built during the NASA Space Apps Challenge 2026, for the challenge "Field Shift: Adapting Farms with NASA Data".

The tool is built to compare crop rotations for a field against the observed climate record. For one rotation on one field, the deployed service repeats the rotation over the agricultural years of the daily climate record of the point, read from NASA POWER, takes soil and slope from a declared file, and reports three indicators: soil loss, exposure to water deficit and the trend of soil carbon. A value that cannot be computed is reported as missing with its reason, never as zero. With `205` signed parameter records in `params/records/` and `6` signed properties in `data/demo/la_estanzuela_soil_slope.json`, all six core engines (`EP1`–`EP6`, `6/6` operational engines) run across both D128 demonstration rotations (`soybean-winter-fallow` and `wheat-soybean-maize`). The example rotation of the repository, which the live-data action of the interface sends, has placeholder crops with no water or residue record, so its answer carries missing inputs for water and carbon. Soil loss carries no uncertainty range, and at the demonstration point it overestimates the loss measured on local runoff plots about 6 times (decision D148 of issue #77). The comparison between rotations is a separate decision layer: when the data cannot separate two rotations, it names the pair as not separated, with the reason, and lists what to measure first. The service has a route that runs that layer on the output of two rotations (PROPOSED, D198), and the decision section of the interface shows the document it returns for the two rotations of the demonstration. A third route, `POST /api/plant/run` (PROPOSED), answers "What should I plant?" for three to five rotations of one field from the economic facts the user declares, and the `#/plant` screen of the interface asks it when a service is configured.

Three terms used below. An agricultural year is twelve consecutive calendar months beginning at the start month of the case; in the demonstration the start month is 7, July. `C` is the cover and management factor of the soil-loss equation: the declared `C` is one value, declared by the lead developer from a published measurement of continuous no-till cropping in Uruguay (D125), and the computed `C` is worked out for each agricultural year from canopy cover and residue cover. EP1 is the entry point of the soil-loss engine, the one function through which the service calls it (`contracts/ENTRYPOINTS.md`).

**Soil loss** (`engine/erosion/`). The engine computes the annual soil loss of the Revised Universal Soil Loss Equation, `A = R · K · LS · C · P`, for each agricultural year that the climate record covers whole. Its parameters are records of `params/records/`, each checked or declared by the lead developer and signed. For the demonstration point, La Estanzuela, with the single declared `C` of decision D125, the figure is 2.365 t ha-1 yr-1, "based on a Uruguayan no-till measurement; overestimates about 6 times the loss measured on the La Estanzuela plots in 2017–2019 (Grahmann et al. 2022)" (the label of decision D148). The comparison with the measured plots and its result are in [docs/VALIDATION.md](docs/VALIDATION.md#ep1-plausibility-against-the-la-estanzuela-runoff-plots-20172019-e7), entry "EP1: plausibility against the La Estanzuela runoff plots (2017–2019) [E7]". Decision D213 keeps this single declared `C` for the release: no published source read gives a `C` for both rotations of the demonstration, so there is no `C` per rotation, and soil loss stays the same for every rotation (D158).

The engine also holds a route that computes `C` from canopy cover and residue cover. That route did not pass the same comparison, and D148 withdrew its values from the demonstration. The withdrawal is applied in the catalogue the service loads (D158, D164): the records that only the computed `C` reads are kept, signed and unchanged, in `params/withdrawn/`, which the service does not load. The service therefore gives the declared-`C` figure for every rotation. The interface does not show a value whose source says computed `C`.

## How to run it

The commands below are those of [CLAUDE.md](CLAUDE.md) and of `.github/workflows/ci.yml`. Those two files and [api/README.md](api/README.md) say what each one needs. Run them from the repository root. [docs/WALKTHROUGH.md](docs/WALKTHROUGH.md) (#303) takes a clean clone through them step by step, with the output each one gave at the commit it names.

```bash
uv sync                                  # install, including the dev group
uv run pytest                            # all tests
uv run uvicorn api.main:app --reload     # backend on http://localhost:8000
docker compose watch                     # the whole app: backend on :8000 and frontend on :5173/field-shift-rotation-twin/
```

The backend started with `uvicorn` has no climate source and no soil file configured, and answers with typed absences. The stack started with `docker compose watch` needs the Docker daemon running, not only the `docker` command installed, and has the real climate source switched on, so a rotation request to it calls that source. To start it with the climate source off:

```bash
POWER_SETTINGS_FILE= CLIMATE_START_DATE= CLIMATE_END_DATE= docker compose up
```

The frontend alone, as CI builds it, in `web/`:

```bash
npm ci
npm test
npm run build
```

## Known limits

- The soil-loss figure overestimates the loss measured on the La Estanzuela plots about 6 times, and 2.9 to 17.0 times by year (D148; the entry of `docs/VALIDATION.md` named in "Status"). The plots are on another soil than the soil of the demonstration; the entry records that using the soil of the plots explains at most a factor of 1.3. The engine was not calibrated or tuned.
- The declared `C` is one value for every rotation, so with it soil loss does not separate the rotations of the demonstration (D158).
- The computed `C` did not pass the plot check. Its code and its signed records stay in the repository, outside the catalogue the service loads.
- Soil loss has no uncertainty range, and `R` is the same in every agricultural year: its variation between years is deferred (D69).
- `params/records/soil_loss_tolerance.json` (`7 t ha-1 yr-1`, D213) is now signed in the catalogue (`#563`), while engine/decision `DeclaredLimit` wiring (`NOT_DECLARED` in `POST /api/decisions/run`) and whether secondary sources satisfy `USER-Q` (D74) remain open (`D60`).
- `205` signed parameter records now back all `6/6` operational engines (`EP1`–`EP6`) across both D128 rotations (`27` top-level root, `110` `water/`, `18` `residues/`, `20` `amg/`, `30` `rothc/`), together with `6` signed properties in `data/demo/la_estanzuela_soil_slope.json`; however, local Uruguayan calibration/validation of carbon and water field outputs remains unvalidated, and the `[H10]` runoff check stays `BLOCKED_NOT_EVALUATED` / `not evaluated` across its open human gates.
- The three trivial comparators (D0, E0, H0) run on hand-written example data, and `validation/service_comparators.py` (`W4-04`, `#522`, `PROPOSED`) also compares their orders against live service outputs. With `EP1` soil loss equal across rotations under declared `C`, E0 can only state that the full method gives no order (D211).
- Soil and slope come from one declared file, served as example data for any field (D38). The file of the demonstration point is `data/demo/la_estanzuela_soil_slope.json` (now carrying `6` signed properties). The adapter for soil tables by soil group is built, and no tables have been supplied to it. No elevation model is decided, so it gives no slope.
- A field is one point. The interface requests the centre of the bounding box of a synthetic example field; how the point is chosen for a field is not decided.
- The decision route of the service and the decision section that shows its document (`DecisionSection.tsx`, including `measure_first` and `named_years` from `W4-10`, `#557`) are PROPOSED (D198, #363). Soil loss is the same for every rotation (D158); without `uncertain_inputs` (`W4-05`, `#524`), `measure_first` returns empty (`NOT_DECLARED`). The saved case has a PROPOSED contract (D177); `demo/` writes one for the example case, its copy under `web/src/data/saved_case.json` is checked byte for byte, and `#/saved` (`web/src/saved/SavedCaseScreen.tsx`, `W4-08`, `#527`) renders it offline. ## How we work

Then read [docs/DEVELOPMENT_BLUEPRINT.md](docs/DEVELOPMENT_BLUEPRINT.md) before opening a branch. In short:

- English only, in code, documents and interface text.
- Every piece lands with its acceptance test.
- Every dataset, library, table and publication is recorded in [ATTRIBUTIONS.md](ATTRIBUTIONS.md) when it is first used.
- AI assistance governance and traceability live in [CLAUDE.md](CLAUDE.md), [ATTRIBUTIONS.md](ATTRIBUTIONS.md), and pull request metadata / commit history (`AI_USE_LOG.md` was retired on `main`).
